# hh.ru в Workix MCP

Локальная сессия hh: поиск по залогиненной выдаче, статусы откликов, чтение
переписки и полуручная отправка откликов.

**Куки и сессия hh никогда не уходят на workix.co.** Всё лежит в `mcp/data/`
(в `.gitignore`): jar в `data/cookies/hh.json`, профиль браузера в
`data/browser/hh/`.

---

## Быстрый старт

```bash
cd mcp
npm run hh:login     # откроется Chrome — логин/пароль/код вводишь ТОЛЬКО там
npm run hh:check     # проверить сохранённую сессию
```

Скрипт ждёт, пока hh выдаст куку `hhrole` со значением, отличным от
`anonymous`, затем забирает куки и закрывает браузер. Пароль агент не видит и
не запрашивает — как и в [TELEGRAM.md](./TELEGRAM.md).

Если автодетект не сработал, а ты уже вошёл:

```bash
npm run hh:capture   # снять сессию с уже открытого окна
```

При таймауте окно **не закрывается** намеренно: закрытие потеряло бы
сессионные куки, которые ещё не легли в профиль на диск.

---

## Почему нужен браузер, а не просто куки

Два барьера, оба обходятся не тем, чем кажется.

**DDoS-Guard.** С минимальным набором заголовков `/search/vacancy` отдаёт 403
с JS-челленджем, даже когда куки валидны. Помогает полный браузерный набор
(`Sec-Fetch-*`, `sec-ch-ua`, `Referer`, `Upgrade-Insecure-Requests`) — он в
`webHeaders()` в [`src/adapters/hh.ts`](./src/adapters/hh.ts). После серии
частых запросов челлендж возвращается уже и на главную, поэтому
`fetchHhState()` двухуровневый: сначала быстрый HTTP, при челлендже — тот же
запрос в залогиненном профиле Chrome
([`src/adapters/hhBrowser.ts`](./src/adapters/hhBrowser.ts)).

**Проверка авторизации.** Судить по ответу сервера нельзя: пойманный челлендж
выглядит как «разлогинен». Источник истины — кука `hhrole`.

**Парсинг.** hh кладёт SSR-состояние в `<template id="HH-Lux-InitialState">`,
экранированное **числовыми** сущностями (`&#34;`), а не именованными.
`textContent` на `<template>` пустой — содержимое лежит во фрагменте, поэтому
из DOM его так не достать; на сервере работает регулярка по сырому HTML.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `workix_hh_status` | жива ли сессия, когда истекает, есть ли `HH_APP_TOKEN` |
| `workix_hh_negotiations` | статусы откликов: отказ, приглашение, где ждут ответа. **Только чтение** |
| `workix_hh_sync_outreach` | переносит эти статусы в локальный `outreach`, чтобы дайджест не предлагал вакансии, на которые уже откликнулись. Идемпотентно, hh только читается |
| `workix_digest` (платформа `hh`) | поиск по залогиненной выдаче |

`api.hh.ru` анонимно отдаёт `{"errors":[{"type":"forbidden"}]}` — публичного
доступа больше нет. Адаптер идёт через залогиненный сайт, а API остаётся
запасным путём, если появится `HH_APP_TOKEN` с https://dev.hh.ru.

## Отклики и сообщения

```bash
node scripts/hh-apply.mjs --id 135589354 --text-file letter.txt          # проверка
node scripts/hh-apply.mjs --id 135589354 --text-file letter.txt --send   # отправка
node scripts/hh-chat-send.mjs --chat 5536866857 --text-file msg.txt --send
```

Один отклик за запуск, по явному `--send`. Отклик отозвать нельзя.

После подтверждённой отправки скрипт сам пишет строку в локальный `outreach`
(`channel=hh`, id `hh-apply-<vacancyId>`, полный текст письма). Без этого
дайджест не знает об отклике — он отсеивает отработанное только по таблице
`outreach` — и вакансия всплывает снова через несколько дней (так вернулась
`135881782`). Если отправка не подтвердилась (кнопка отклика осталась), строка
пишется как `draft`. Отклики, отправленные руками на сайте, подбирает
`workix_hh_sync_outreach`.

### Три грабли, на которые уже наступили

Каждая стоила реального отклика на живом аккаунте. Не убирать защиты.

**1. Поле хранит черновик.** hh восстанавливает ранее набранный текст. Ввод без
очистки вставляется от позиции курсора — письмо уходит задвоенным и
перемешанным. Всегда `Ctrl+A` + `Backspace` перед вводом.

**2. `page.type()` проигрывает `\n` как Enter.** На вакансиях, где
сопроводительное необязательно, это отправляет отклик посреди заполнения —
«сухой» прогон перестаёт быть сухим. Переводы строк вводить только как
**Shift+Enter**.

**3. Нативный сеттер `value` не обновляет состояние React.** В DOM текст есть,
для hh поле пустое: кнопка отправки не срабатывает, а отклик ушёл бы с пустым
письмом. Вводить настоящими нажатиями клавиш, не присваиванием.

Отсюда же правило: **клик по «Откликнуться» сам по себе может быть откликом.**
Если сопроводительное необязательное, модалка не открывается, а отклик уже
создан — hh потом лишь предложит приложить письмо. Считать «открыл форму»
безопасным действием нельзя.

### Что обязано быть в любом таком скрипте

- сверка набранного текста с утверждённым **символ в символ**, иначе отмена;
- подтверждение по факту (поле очистилось, кнопка отклика исчезла после
  перезагрузки), а не по тому, что клик вернул управление;
- скриншот до и после в `data/apply-shots/`;
- отказ работать, когда форма незнакомая — например, у вакансии вместо письма
  анкета (`vacancy-response-question_*`). Гадать нельзя, это к человеку.

### Отправка в чат

Кнопка `chatik-do-send-message` сама по себе не отправляет — реальный путь
Enter в поле ввода. Проверка успеха — поле очистилось. Доступность переписки
видна в `inboxAvailabilityState`: `WITHOUT_INVITATION` значит, что свободные
сообщения до приглашения работодателя не пройдут.

## Что проверять глазами, а не регуляркой

hh поставляет **все строки интерфейса** в JS-бандле и в SSR-payload. Наивный
поиск подстроки по HTML поэтому врёт:

- «Вы откликнулись» есть на **каждой** странице вакансии. Признак уже
  отправленного отклика — **отсутствие** кнопки `vacancy-response-link-top`;
- «вакансия в архиве» есть и на живых вакансиях. В
  [`src/freshness.ts`](./src/freshness.ts) перед проверкой маркеров вырезаются
  `<script>`, `<template>` и `<noscript>`.

Правило простое: прежде чем поверить признаку, проверить его на заведомо
противоположном случае. Обе ошибки выше нашлись именно так.
